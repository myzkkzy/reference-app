# 要件の記述

共通原則と権限は[スキルの入口](../SKILL.md)に従う。

## 入力と出力

- 入力：実在する要求本文、参照時点・合意状況、指定制約、既存要件、適用規則。
- 出力：要件本文、要求との対応、依存関係、未決事項、設計への検討事項。

## 手順

- 入力要求の本文・根拠・合意状況を確認する。要求がなければ不足を返す。
- 本文と受入条件の機能・非機能・制約を区別する。操作・設定・通知・再試行は機能、性能・容量・復元保証は非機能として扱い、倍率・間隔など操作仕様の数値を品質条件と混同しない。種類の制約表記と保存先の分類は適用規則に従う。
- 混在する独立条件は適用規則に従って別文書へ分割する。既存ID・状態を保持し、追加分を未使用ID・ドラフトとして新旧関係を本文へ記録する。意味、数値、保証範囲、根拠、未決事項と受入条件を引き継ぎ、元の操作・通知・回復手順には抽出先の正本への参照を残す。
- 適用条件、正常・異常の振る舞い、業務ルール、権限、情報の意味を記載する。
- 外部連携は期待するやり取りとして記載し、APIやDBの構造を確定しない。
- 参照要求の要約・状態・リンク、優先度と理由、根拠、依存・未決を残す。
- 設計時の見直し結果は適用規則で認められた判断記録と上流判断を確認して反映する。設計の具体化への依存を要件へ持ち込まず、本文・受入条件・引継ぎだけで期待する結果を読めるようにする。
- 要求から優先度を自動確定せず、無関係な要件を網羅目的で増やさない。
- 未合意や矛盾に依存する部分は確定せず、独立部分の具体化を続ける。
- 要件全体の依頼では受入条件の手順も使い、その結果を本文に組み込む。

## 参照資料

- 受入条件も作る依頼：[受入条件の作成](acceptance-criteria.md)。
- 条件の結果を本文へ組み込む。既存条件がある場合はその内容と適用範囲を保持する。

- 対応する成果物を作る場合：[テンプレート topic.md](../assets/templates/topic.md)。
- 対応する成果物を作る場合：[テンプレート cross-cutting.md](../assets/templates/cross-cutting.md)。

## 確認例

- 入力：参照要求の一部が矛盾している。
- 期待：影響部分を確定せず、独立部分を具体化する。架空の要求を作らない。
