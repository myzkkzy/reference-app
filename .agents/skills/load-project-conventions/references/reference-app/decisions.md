# 判断記録の規則

## PDR

- 保存先は docs/product-demands/product-decisions/ とする。
- index.md はリンク専用の一覧とする。
- 判断日と英小文字kebab-caseのテーマを組み合わせたファイル名とする。
- 判断日が不明なら記録日を使い、同日・同テーマはテーマ名を具体化して区別する。
- 独自の出典IDや連番IDを付けず、文書名・該当節へ相対リンクする。
- 判断日・記録日、背景、決定内容、理由・根拠、関連要求を記載する。
- 本人申告の現状は背景に置き、決定事項と分ける。
- 対話の日付・取得経路と、要約か逐語引用かを明示する。
- 不明な原文や未回答の理由を補作しない。
- 未決事項・後続判断や、それらへの参照欄はPDRに設けない。
- 未決は要求の「未決事項・仮定」「要件定義への引継ぎ事項」で管理する。
- PDRの決定を要求全体への合意、開発決定、需要の実証と同一視しない。
- 文書管理方式は担当指示とテンプレートで管理し、プロダクト判断に混ぜない。

## ADR

- 保存先は docs/product-design/architecture-decisions/ とする。
- 命名は <YYYY-MM-DD>-ADR-<ID>-<topic>.md とする。
- 日付は作成日であり、採用・更新時も維持する。IDはプロジェクト全体の連番とする。
- 一覧の列はADR-ID・タイトル・状態・本文リンクとする。
- アーキテクチャ、技術選定、保存・移送・描画、重要なテスト基盤・検証方式を対象とする。
- 本文は現在の構造、ADRは選択理由を管理する。局所的判断は本文へ記載する。
- ID・タイトル・状態・作成日・決定日、背景・制約、関連DEM/REQ/DESを記載する。
- 候補・判断基準、決定・理由、利点・不利益・リスク・影響も記載する。
- 根拠資料と確認日・試作結果、判断権限、未決条件・置換関係も記載する。
- 状態は提案・採用・却下・置換済み・廃止とする。
- 合意済み要件内で完結し根拠が揃う通常の技術判断は、設計担当が採用できる。
- 要件変更や本人合意が必要な条件がある場合は、上流判断・反映まで提案に留める。
- 全ADRの本人承認は求めない。ADRで要件合意を代替しない。
- 採用判断の変更は新しい作成日・IDで作り、旧ADRを置換済みにして相互リンクする。
- 旧理由は保持する。適用終了のみなら理由を残して廃止にする。
- 誤字・リンク修正は同じADRで行う。
