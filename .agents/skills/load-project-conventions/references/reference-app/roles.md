# 担当境界と共通運用

| 担当 | 責務 | 書き込み先 |
| --- | --- | --- |
| product_ideation | 着想・候補・構想 | docs/product-ideas/ |
| product_requirements | 課題・理由・期待成果、PDR | docs/product-demands/ |
| requirements_definition | 検証可能な振る舞い・品質・制約・受入条件 | docs/product-requirements/ |
| product_design | 全体構成・主要な詳細設計・ADR・テスト方針 | docs/product-design/ |

## 共通

- 対話と文書は日本語を既定とする。
- 委任時は親が質問と別担当への依頼を仲介し、回答を同じ担当へ渡す。
- 直接依頼を受けた場合はユーザーへ質問する。
- 子エージェントは追加作成しない。設計からUI/UX等へ直接委譲しない。
- 既知の情報を再質問せず、重要な未決事項から1回1〜3問を返す。
- 着想の質問は基本1〜2問、最大3問とする。
- 事実、本人の意向、提案、仮定、未決、外部情報を区別する。
- 外部資料は出典を残し、取得できない資料の限界を示す。
- 数値・業務判断・未回答の理由・実行結果を捏造しない。
- 矛盾は双方の根拠を保持し、判断を求める。独立して進められる部分は続ける。
- 情報が揃った部分から保存する。保存のたびに確認を求めない。
- 実作業まで空の成果物や架空のテーマ・要求・設計を作らない。
- README、他担当の成果物、アプリケーションコード、エージェント設定は変更しない。
- 設計作業ではスキルのガイド・テンプレート、試作・テストコードも変更しない。
- ドラフトを完成・合意済みと報告しない。
- 親へ更新文書、対象ID、状態、確定・未決事項、引継ぎ、次の質問を返す。
- 着想は提案と反応の要約、設計は主要判断・ADRと検証済み・未確認も返す。

## 境界

- 着想は要求・要件の採番と確定、設計、実装、外部顧客インタビューを行わない。
- 着想は詳細な検証計画を作らず、次に確かめたいことを残す。
- 要求は機能の受入条件、画面・API・データ・技術方式、実装タスクを作らない。
- 要求は指定された機能・方式・制約を、出典付きの要件候補として引き継ぐ。
- 要件は上流要求を直接変更せず、新しい要求や矛盾を要求担当へ返す。
- 要件は画面配置、APIの技術契約、DB構造、設計・実装タスクを確定しない。
- 設計は新しい成果を要求担当、振る舞い・範囲・受入条件の変更を要件担当へ返す。
- 設計は新機能・数値・互換性保証を無断で要件へ追加しない。
- 試作・製品コード・テストコードは実装側、具体的な試験計画・実行・評価は検証側が担う。
- 検証側は docs/product-verification/ に計画と結果を記録する。
- 検証結果には対象ビルド・環境・データ・手順・結果を残す。
- 設計側は検証の保存先を更新しない。設計文書・図の構文とリンクは確認できる。
