# 既存動作の回帰シナリオ

静的レビュー用の観点であり、実行済みの試験結果ではない。

## product-ideation：確認シナリオ

| 入力・状況 | 期待する対応 |
| --- | --- |
| 「何か作りたい」のみ | 興味や経験を少数の質問で聞き、異なる切り口の案を提案する |
| 既に案がある | 案を尊重して深掘りから始め、必要に応じて別の切り口を広げる |
| 「分からない」が続く | 同じ質問を繰り返さず、具体例や仮案への反応を聞く |
| 比較しても選べない | 複数案を維持し、保留や掘り起こしへの回帰を認める |
| AIが利用場面を描く | AIの仮説と明示し、顧客の発言や需要の実証にしない |
| AIが推奨しただけ | ユーザーが選択するまで検討中とし、引継ぎ候補にしない |
| 引継ぎ候補になっただけ | 要求定義を自動開始しない |
| 引継ぎ対象をユーザーが指定 | 構想と未確認の仮説を渡し、要求の合意済み扱いをしない |
| 保留・見送り案を再開 | 以前の判断理由を読んで再検討し、変更理由を残す |
| 要求定義から再検討を依頼 | 構想を見直して変更点を返し、要求文書は直接変更しない |

## product-requirements：確認シナリオ

| 入力・状況 | 期待する対応 |
| --- | --- |
| 「便利なサービスを作りたい」のみ | 課題・対象者・期待成果を少数ずつ質問し、架空の要求を作らない |
| 対話でプロダクトの判断が確定 | テーマごとのPDRに記録し、要求から参照する。未決事項・後続判断は要求で管理する |
| indexの更新 | 一覧と参照先だけを記載し、範囲・未決事項は各要求に記載する |
| 特定の通知方式などの機能提案 | 背景の要求を確認し、方式は要件候補として引継ぎ節に分離する |
| 異なる業務責務に関する複数の要求 | 分類ディレクトリ内へ1 DEMにつき1ファイル・IDと英語の内容名を組み合わせた名前で保存し、共通要求は参照する |
| 既存要求の変更・移動 | IDを維持し、影響する文書・矛盾・合意状況を確認する |
| 成功指標の数値や方針が未回答 | 未決と記録し、ユーザーが合意したように扱わない |

担当範囲の指示とファイル単位のアクセス制御は別である。実際の権限は親セッションの設定に従う。

## requirements-definition：確認シナリオ

| 状況 | 期待する動作 |
| --- | --- |
| 合意済み要求から機能を具体化 | 受入条件のケースを「正常」「異常」に分類し、関連する異常時の対応も扱い、DEM-IDと関連付ける |
| 性能目標の閾値が未指定 | 数値を捏造せず、評価条件・基準の質問を返す |
| 一部の要求が矛盾 | 関連要件だけ保留し、独立した要件はドラフト化する |
| 元の要求が変更 | 依存要件・受入条件・対応表を確認し、影響する状態を戻す |
| 複数テーマに共通する要件 | 横断分類の独立したREQ-IDと英語の内容名を組み合わせたファイルに本文を置き、各分類から同じREQ-IDを参照する |
| 対象要求に対応要件がない | 未着手・保留を明示し、対応漏れとしてレビューする |
| 要件の根拠となる要求がない | 要求担当へ差し戻し、架空のDEM-IDを付けない |
| indexの更新 | 全要件一覧・全対象DEMの対応表・参照先に限定し、詳細は本文に残す |
| 今回要件化しない要求がある | 関連本文の「要求担当への確認」にDEM-ID・リンク・除外理由を記載し、REQ-IDを作らない |
| 要件の変更・合意 | 本文と現在の合意状況・根拠を更新し、履歴の節・表や代替文書を作らない |
| 要件の分割・統合・廃止 | 新旧ID関係を該当本文に記載し、廃止状態を明示してIDを再利用しない |
| 横断文書の分割 | 分割先を分類ディレクトリ内のREQ-IDと英語の内容名を組み合わせたファイルに置き、要求対応表は全体索引に維持する |

## product-design：エージェントの確認シナリオ

以下は設定・ガイド・テンプレートの確認であり、アプリの要件充足・性能達成の判定とは区別する。

| 入力・状況 | 期待する動作 |
| --- | --- |
| TOML読み込み | 必須3項目をパースでき、モデル・権限の上書きがない。新規セッションでの認識は別途確認 |
| 対象REQ一覧 | 全件をDESまたは未対応理由へ関連付け、架空IDや対応漏れを作らない |
| 条件付き合意 | 進行範囲を守り、必要なユーザーの合意と上流反映まで未決を維持する |
| 保存競合・異常終了 | 順序・保護範囲・観測点を設計し、必要な試作と各テスト層へ引き継ぐ |
| 原本なしの再開 | 保存データと一時/再生成データを区別し、欠落・参照整合性を扱う |
| 要件変更 | DES・図・データ・ADR・テスト方針・引継ぎまで影響を追い、無関係な状態は維持する |
| ADR採用・変更 | 通常判断と上流判断を区別し、命名・作成日・ID・置換リンクを守る |
| 全体設計の技術スタック | 独立した見出しで、フロントエンド・バックエンド・フォーマッター・リンター・テスト・ビルドと必要な追加分類の技術・利用箇所・用途を説明する。採用状態・比較・根拠はADRへ集約して参照し、未選定の技術を補作しない。品質・配布条件と未検証事項は設計本文に残す |
| 試作・検証担当なし | 役割宛てに具体的な依頼を返し、コードや架空結果を作らない |
| データ構造 | 図の多重度、項目の型/任意性/単位、参照・削除・保存契約が整合する |
| API・IPCの選定 | 必要な操作・境界・状態の所有者・完了条件から入口を導出し、根拠要件・依存設計と独自案/既存APIを追跡する |
| パラメータ定義 | 入力4列・出力4列に論理名・物理名・通信上の型・説明を示す。共通型・複合型を参照し、DB列を通信キーと混同せず、左右の行の対応を仮定しない |
| 非同期IPCの完了 | 受付・後続通知・最終結果・エラーの経路/時点/項目と要求との対応を区別する。バイナリの相関をJSONフィールドの返却と混同しない |
| 未定義の通信契約 | フィールド・包絡・相関や採用/破棄等の不足を明記して引き継ぎ、入口一覧を網羅済み・設計を実装引継ぎ可能としない |
| データ・画面の詳細設計 | 全体設計の3図を保持し、詳細は専用ディレクトリの独立DESへ分け、全体・テーマ設計と相互参照する。下位索引には説明付き文書リンクだけを置く |
| 画面遷移図・構成図 | 必要な詳細図を編集可能な.drawio.svgで作り、画面設計本文に埋め込む。全体設計の3図とデータのクラス図はMermaidを維持する |
| 画面構成図の更新 | 低忠実度ワイヤーフレームで画面部品を配置し、状態差分を部分図で示す。説明は画面外の注記に置き、本文・未決表示と同期する |
| 画面遷移図の更新 | 操作別部分図と明示した再掲ノードで入口・成功・取消・失敗を追跡でき、線の交差・重複・無関係なノード通過を出力画像で確認する |
| 図の更新・失敗 | 埋込データから編集し、元の要素IDと接続を保つ。出力・検査失敗時に既存図を保護し、未決事項を確定扱いにしない |
| 別分野・画面なし | 外部との処理の流れを示し、不要なUI・DB・画像固有条件を追加しない |
| 文書レビュー | 設定・ガイド・テンプレート間の責務/状態/命名が一致し、リンク先・見出し・Mermaid表示を確認する |

現行プロダクトの要件を入力例にレビューできる。件数・画像構成・性能数値を共通指示やテンプレートに固定しない。
確認できなかった項目は未確認として報告する。


## 分類別構成と本文中心の進行

以下は静的レビューの観点であり、実際のエージェント実行結果ではない。

| 入力・状況 | 期待する対応 |
| --- | --- |
| 単純な機能要求から開始 | 背景・用語・操作の流れを必要な本文に記載し、専用の業務補助資料を前提にしない |
| 工程ごとに適切なテーマが異なる | 各工程で整理し、フォルダやテーマ名の一致を強制せずIDで対応を追跡する |
| 共通の用語や説明が必要 | 関連する要求・要件本文を管理元とし、他から参照する |
| 設計から要求の目的・意味を変更する提案 | 根拠・影響を要求担当へ返し、反映まで確定しない |
| 設計から振る舞い・業務ルール・受入条件を変更する提案 | 根拠・影響を要件担当へ返し、独立した設計を続ける |
| 保存失敗・同時更新を含む機能 | データ整合性・更新単位・競合制御・失敗時の保護と回復を設計する |
| 文書の配置変更 | ID・本文の意味・受入条件・数値・合意根拠・未決・廃止状態を保持し、参照を更新する |
| 既存設計の分割 | 旧DESの処理・履歴と新DESのデータ・画面の正本を分け、ADR・要件対応表・見出しリンクを更新する |
| 要求に複数テーマの要件が対応 | 全体索引の一つの対応表に全関連REQを掲載する |
| 廃止・対象外の要求 | 本文の理由へ参照し、架空の要件や新IDを作らない |

## 参照方向と設計時の上流見直し

| 入力・状況 | 期待する対応 |
| --- | --- |
| 要件の根拠欄に設計へのリンクがある | 判断根拠をPDRの決定内容へ整理し、要件から設計への参照を除く。振る舞い・受入条件・合意状態は維持する |
| 引継ぎにリンクのない下流IDがある | IDだけの参照も除き、上流本文自身の条件と担当役割で検討事項を記載する |
| 設計から要件を参照する | 参照を維持し、対象REQと受入条件を追跡できる |
| 同工程の共通ルールを参照する | 同工程内の参照を維持する |
| 上流変更の影響を調べる | 下流の上流参照と対応表から調べ、上流に逆向きリンクを追加しない |
| 設計時に上流の変更が必要になる | 確認できる理由・対象・変更案・判断状況をPDRまたはADRへ残し、親経由で担当へ返す |
| PDR・ADRから発端の設計や見直し対象を参照する | 判断記録の例外として許可する。要求・要件はPDRの決定内容を参照し、設計・ADRへ依存させない |
| 必要な上流判断・反映が未完了 | 技術案は提案に留め、PDRを未決事項の台帳にしない |
| 既存文書から判断記録を整理する | 出典は既存文書の要約と明示し、不明な日付・原文・理由を補作せず、個別判断を全体合意にしない |

## 1項目1ファイルの確認

| 入力・状況 | 期待する対応 |
| --- | --- |
| 新しい構想・要求・要件・設計の保存 | 工程全体の連番を確認し、分類内のIDと英語の内容名を組み合わせたファイルへ1項目だけ記載する |
| 同じ接頭辞のIDが別分類に存在する | 分類ごとに連番をリセットせず、既存・廃止IDと重複させない |
| 分類変更・移動 | ID・本文・状態を保持し、相対リンクと工程・分類索引を更新する |
| 複数項目に共通する要件 | 独立REQを採番し、適用先・根拠・受入条件を保持する。採番を新たな合意と扱わない |
| 分類索引の更新 | 説明付き本文リンクだけを置き、全ID一覧・対応表・候補状態を工程索引へ集約する |
| 複数REQに対応するDES | 1 DESにつき1ファイルとし、REQごとに同じ設計を複製しない |
| PDR・ADRの参照更新 | 日付付きファイル名・判断内容・状態を保持し、移動先本文への参照を更新する |

| 入力・状況 | 期待する対応 |
| --- | --- |

## 機能・非機能の分離と階層索引

| 入力・状況 | 期待する対応 |
| --- | --- |
| 要件の操作・通知と性能・容量・復元保証が混在 | 本文と受入条件を分割し、操作・通知・回復手順は機能側に残して品質条件の正本を参照する |
| 倍率・グリッド間隔・自動保存周期などの数値 | 操作・設定仕様として機能に配置し、数値の有無だけで非機能に分類しない |
| 種類が「制約」の既存要件 | 本文表記を保持し、定める対象に応じて機能・非機能へ配置する |
| REQ-029の利用上限と画像作業先が混在 | 利用上限はREQ-029、作業先操作はREQ-038、画像実体・復旧候補の保護はREQ-039を正本とする |
| 既存REQ・DESの移動と追加分割 | 既存ID・状態を保持し、追加文書に全領域で未使用のIDを付けてドラフトとする。双方へ新旧関係を記載する |
| 分割前後の内容確認 | 意味・数値・保証範囲・受入条件・根拠・未決の対応を確認し、分割元の合意を追加文書への新たな合意と扱わない |
| 構成・データ・画面の品質詳細が混在 | 各定義を残し、非機能設計の正本への参照を置く。画面配置やデータ項目を品質文書へ重複移動しない |
| IPCの移行 | 通信項目・型・受付応答・後続通知・最終結果・エラー・資源寿命を保持し、参照の移行だけで契約を変更しない |
| 品質の見出しを別文書へ移動 | 古いファイルに見出しが残っていても、詳細条件を管理する移動先の正本へ参照を更新する |
| 多段索引の更新 | 工程に全ID一覧と上流対応表、種別・領域に説明付き下位索引・本文リンクを置く。空領域を作らず本文へ到達できる |
| 分割で追加した要件・設計 | 全REQが要求対応表、全DESが要件対応表から追跡でき、本文の根拠と一致する |
| 設計値と未検証の品質条件 | 初期予算・仮定・保証の除外と検証待ちを引き継ぎ、移行を性能達成や実装引継ぎ可能の根拠にしない |
