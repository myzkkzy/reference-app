# 設計の進行手順

[共通の担当境界](../roles.md)と[文書規則](../documents.md)を先に読む。
[状態規則](../states.md)を確認し、対象の状態と許可された進行範囲を守る。
PDR・ADRを扱う場合は[判断記録](../decisions.md)も読む。

文書の作成・更新前に[根拠・出典と合意状況](../documents.md#根拠出典と合意状況)を確認し、内容の根拠文書と判断記録の不足を整理する。回答の逐語引用・承認経緯を出典にせず、既存の合意状況を正本とする。担当外のPDR・ADR不足は親経由で管理担当へ渡す。

## 進行の選択

- 新規全体設計・再開・設計変更は[design-product](../../../../design-product/SKILL.md)の入口から[汎用設計ワークフロー](../../../../design-product/references/workflow.md)を読み、開始位置と必要な操作を選ぶ。6段階の順序・入力・成果物・完了条件・戻り先は同手順を正本とする。
- 新規全体設計は全体方針と責務・境界を整理してからテーマ別に反復する。再開・変更は既存DES・未決・受領結果と変更影響から必要な段階へ戻る。
- 単独操作の依頼では下表の該当操作だけを選び、全体設計や他操作を自動開始しない。
- 進行段階は報告で示し、DES状態・REQ合意・ADR採用・試験合格と区別する。段階別の状態・台帳・文書分類を追加しない。
- 各段階の結果を共有し、重要な未決・上流変更時に判断を求める。保存や全段階の終了で一律のユーザー確認待ちを追加しない。

## 進め方と完了確認

- 共通戦略の概要からテーマ別戦略を具体化し、確定した判断を分析・テスト設計へ渡す。戦略判断→COND群・共通仕様→CASEの対応は設計本文を正本とする。依頼操作と変更影響の範囲だけ扱い、未決に依存する判定は保留する。
- DEM・REQ、受入条件、状態、依存、引継ぎ、既存設計・ADR・コード・検証計画を読む。
- 条件付き合意の許可範囲を守り、独立して進められる設計を続ける。
- 全体構成からテーマへ具体化し、局所的なコード構成は実装担当へ残す。
- 全体設計・テスト方針・テスト設計もDESとして管理し、該当REQとの対応を記録する。技術契約だけの条件・ケースはDESを根拠とする。
- 全体構成の3図を残し、データ設計・画面設計は独立した全体・テーマ別DES文書へ分けて参照する。引継ぎの記載枠は該当DES本文へ挿入する。
- 画面設計に図が必要な場合はdrawio-ui-designを使い、同スキルの出力・検査スクリプトで`.drawio.svg`を生成する。構成図は低忠実度ワイヤーフレームとし、遷移図は線の交差・重複・無関係なノード通過を除く。対応する画面設計本文から埋め込み、図・本文の未決事項を揃え、出力画像を全体と拡大で点検する。
- 要求の目的・意味の変更は要求担当、振る舞い・業務ルール・受入条件の変更は要件担当へ親経由で返す。
- 上流の見直し理由・対象DEM/REQ・変更案・判断状況を判断記録の規則に従いPDR・ADRへ残す。PDRの作成・更新は親経由で要求担当へ渡し、必要な上流判断・反映まで技術案は提案に留める。
- 設計から上流本文を参照し、上流に設計への逆向き参照を追加させない。影響確認は設計側の要件対応表と上流参照を使う。
- 方針・条件分析・具体的ケース、データ仕様、環境要件、準備・操作・後片付け、観測・障害制御方法の文書設計にはdesign-product-testsを使う。単独操作では必要な操作だけを行う。
- 実データ生成・環境構築・テストコード化・実行準備・実行時期の計画・実行・製品結果評価は後続担当へ渡す。具体的な試作・計測も担当役割宛てに必要な証拠と解消条件を整理する。
- ケース・手順不足はテスト設計、契約矛盾・観測不足は製品設計、振る舞い・品質基準・受入条件不足は要件担当へ返す。独立部分を継続する。
- 設計レビューの完了条件を満たした範囲だけ実装引継ぎ可能とする。
- 親へ対象REQ/DES、現在の段階、具体化した条件・ケースの範囲（DES-IDと文書内ID）、主要判断・ADR、確認済みと未確認、未決・引継ぎ、次の作業を返す。文書設計完了・実行準備・試験合格を区別する。単独操作では当該操作と完了した範囲を報告する。

## 分類・分割の確認

- 文書規則の6分類とADR・テスト方針・テスト設計から配置を選ぶ。機能・非機能設計には領域階層を使い、構成・データ・画面・IPCには各定義と詳細設計への参照を残す。
- 処理手順と品質・資源・復元保証の混在を検出し、別DESへ分割する。追加DESは未使用の連番・ドラフトとし、分割元の根拠・未決・初期設計値・保証範囲・未検証の記載を保持する。
- IPC移行では通信項目・型・応答・通知・資源寿命を維持し、機能・非機能の正本への参照で契約との関係を示す。
- 全REQの対応と全DESの追跡、工程→種別→領域→本文の到達性、移動した見出しへの参照を確認する。空の領域は作らない。
