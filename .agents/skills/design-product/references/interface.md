# インターフェース設計

共通原則と権限は[スキルの入口](../SKILL.md)に従う。

## 入力と出力

- 入力：必要な操作と要件、状態の所有者、機能・データ設計、既存の通信契約。
- 出力：境界ごとの通信項目・型・応答・通知・資源寿命と、根拠・依存・未定義の契約。

## 手順

- 概要では、機能の操作・状態・完了条件と構成境界から必要な通信経路・責務を抽出する。テーマ別の概要入力で経路を検討でき、全設計の完成を待たない。
- 詳細では、対象経路に必要なデータ項目、操作・通知・処理結果から通信上の入力・出力・応答・エラー・資源寿命を具体化する。内部モデルと通信表現の対応を確認する。
- 整合確認で状態の所有者・完了条件・表現の前提が変われば、関連する機能・データ・画面・品質設計へ返す。全体進行・変更の戻り先は[設計ワークフロー](workflow.md)で選ぶ。

- API・IPCを設計する場合は、必要な操作から境界を越える処理を抽出し、状態の所有者・責務・完了条件を確認して入口を命名する。根拠要件・依存設計と、独自の設計案か既存APIかを区別する。
- インターフェースの概要には論理名・物理名・呼出元/呼出先・責務・根拠を記載し、パラメータの詳細は[インターフェース契約の記載枠](../assets/templates/interface-contract.md)を使う。適用先の形式に従い、入力と出力を区別して各項目の論理名・通信上の物理名・型・説明を定義する。
- 型は通信上の表現を示し、必須性・範囲・単位・欠落とnullの扱いは説明に記載する。共通型・複合型は項目別に一か所で定義して参照し、JSONキー、内部の型名、DB列を混同しない。
- 非同期契約は受付応答・後続通知・最終結果・エラーの経路と発生時点を区別する。バイナリ本文とJSON包絡、要求との対応方法、処理完了と表示完了を明記する。
- 必要な通信経路の網羅性を確認する。既存資料から定義できない名称・型・対応関係は「未定義」と記載して引き継ぎ、根拠のないフィールドや完了結果を補作しない。
- 所有・採用・破棄・解放、取消や失敗時の資源寿命を定義する。品質条件は[非機能設計](non-functional.md)の正本を参照し、通信上の型・範囲・応答保証に必要な定義は契約側に残す。
- 移動・分類変更では項目名、型、必須性、応答・通知の時点、相関、資源寿命を変更しない。分割先の正本と見出しを参照し、未定義事項・根拠・状態を保持する。
- 保存先と文書単位は適用規則から解決する。共通型を複製せず、関連設計と上流対応表、各階層の索引を同期する。
