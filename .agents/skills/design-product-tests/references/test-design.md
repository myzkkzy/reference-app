# 具体的なテスト設計

共通原則と権限は[スキルの入口](../SKILL.md)に従う。

## 入力と出力

- 入力：対象条件と根拠、受入条件・設計契約、観測・制御方法、既存ケース、依存・未決と進行範囲。
- 出力：条件と対応するケース、入力・データ仕様・環境要件・準備・操作・後片付け、期待結果と根拠、残件・引継ぎ。

## 手順

- 適用する共通・テーマ別戦略へのリンクと「戦略判断の具体化」表を設計本文に置く。列は「戦略本文・見出し／判断の要約／対応COND群・共通仕様／適用・未決の説明」とする。重要な判断の具体化先、未決・適用外の理由を示し、戦略からCASEへは既存COND→CASE対応を使う。
- 対応表の正本は設計本文とし、索引へ複製しない。局所CASE変更では該当COND・共通仕様・根拠への影響を確認し、網羅方針・境界・前提を変える場合だけ戦略へ返す。
- 対象条件・契約の概要からケース案を開始できる。未確定の仕様・評価条件に依存する判定は暫定とし、独立部分を具体化する。全文書の完成待ちを循環させない。
- ケースだけの依頼では既存方針・条件を使い、不足する対応を確認する。入力を無断で再設計せず、足りない条件・根拠は確認事項として返す。
- テーマまたは検証境界ごとの本文に条件・ケースをまとめる。文書IDは適用規則から採番し、ケースごとに文書を作らない。ローカルIDは編集で維持し、廃止IDを再利用しない。
- ケースには名称、対応条件、確認層、種別・品質観点、前提状態、具体的入力・データ仕様、環境要件、準備・操作・後片付け、期待結果と根拠、観測・障害制御方法を記載する。共通定義を一か所に置き、ケースは参照と差分を示す。
- 期待結果は受入条件または確定した技術契約から導く。実装の現在の挙動だけを期待値にせず、値・境界・許容差の根拠を示す。技術契約確認を新しい製品受入条件へ昇格させない。
- 非同期・競合・取消・失敗回復では、状態・順序・成功境界・保護対象を観測する。受付だけで完了判定せず、後着結果や保存中変更等の関連契約を照合する。
- データは代表値・境界値・形式・内容・量・取得/生成方法を仕様化する。環境は上流条件を維持し、必要な依存・時計・負荷・障害制御・計測開始終了点を具体化する。未定の環境版・閾値・試行回数・保証を補作しない。
- 手動/自動化の想定、テストダブルと実物の境界、準備物・必要な証拠を設計する。実ファイル生成・環境構築・コード化・実行計画の具体的割当て・実行・製品結果評価は後続担当へ渡す。
- 本文内で根拠→条件→ケースを多対多で追跡する。ケース本文を方針・機能設計・索引へ複製せず、変更は依存するケース・共通定義・引継ぎまで追う。

## 完了と戻り先

- [レビュー](test-review.md)を満たした範囲だけ引継ぎ可能とする。実ビルド・データ・環境・コードが未作成でも、準備仕様が確定していれば文書設計の完成を判断できる。
- ケース・手順の不足は本操作、条件の抜けは[分析](test-analysis.md)、分担・評価方針の不足は[方針](test-strategy.md)へ返す。
- 契約矛盾・観測不足は製品設計へ、振る舞い・品質基準・保証の不足は上流担当へ返す。結果受領だけで未決を解消済みにせず、影響範囲を再レビューする。
- 引継ぎでは対象文書・条件・ケースの範囲、準備物、担当役割、必要な証拠、残件と再確認範囲を示す。担当未作成なら役割宛てとし、起動・外部送信は行わない。
