# テスト分析・条件整理

共通原則と権限は[スキルの入口](../SKILL.md)に従う。

## 入力と出力

- 入力：対象範囲、要件・受入条件と状態、テスト方針、責務・状態・不変条件・技術契約、未決。
- 出力：根拠付き条件、網羅対象・技法・優先理由、対応と不足・未決。

## 手順

- 適用する共通・テーマ別戦略と重要な判断を確認し、戦略に基づく分析から条件を抽出する。条件群または共通仕様への対応を設計本文で記録する。戦略判断の不足・矛盾は該当戦略へ返し、独立部分は進める。
- 根拠本文・見出し・対象条件の要約と確認時点を記録し、状態・進行範囲を確認する。受入条件にIDがなくても根拠を識別し、上流へIDや逆向き参照を追加しない。
- 操作・正常／異常・境界・状態遷移・順序・取消・失敗回復、技術契約・品質観点から条件を抽出する。確認対象と期待する保護を示し、製品受入と技術契約確認を区別する。
- 同値分割・境界値・デシジョンテーブル・状態遷移などからリスクに合う技法を選ぶ。代表範囲・境界・規則・遷移等の網羅対象と選定理由を示し、全技法・全層や根拠のない網羅率を要求しない。
- 条件ごとに根拠、確認層と種別・品質観点、網羅対象、優先理由、観測・制御の見通し、未決を整理する。正常／異常は適用規則で分類し、技法と混同しない。
- 条件はテスト設計本文へ置き、適用規則に沿う安定したローカルIDとIDのみの見出しで管理する。ケース未作成なら対応を未作成と記録し、架空のID・リンクを作らない。
- 受入条件・契約から条件への多対多の対応を確認する。対象外・延期は理由と影響を本文に残し、未対応を対応済みとしない。技術契約だけの条件に架空の要件を作らない。
- 品質基準・振る舞いの不足は上流、観測不足・制御不能・契約矛盾は製品設計へ返す。依存条件は暫定とし、独立条件を続ける。

## 完了と接続

根拠・条件・網羅対象・選定理由・未決の影響が識別できた範囲を報告する。判定を左右する未決が残る範囲は確定せず、分析完了をケース設計完了や試験合格にしない。

- 記載枠：[test-design.md](../assets/templates/test-design.md)。分析だけではケース節を未作成とする。
- ケースを具体化する依頼：[具体的なテスト設計](test-design.md)。
- 完了判断：[テスト設計レビュー](test-review.md)。
