# プロダクトのテスト設計

## 文書の表記

- 回答・意向・合意の主体は「ユーザー」、製品の操作・利用条件の主体は「利用者」と記載する。
- 通常の説明文には日付を記載しない。ファイル名・リンク先・メタ情報・明示的な日付項目や日付列、日付形式の仕様・コード例・テストデータは例外とする。
- 期待結果・閾値・保証と判断理由は根拠文書の該当節を照合する。判断記録不足は管理担当へ渡し、会話の回答だけを期待結果や合意の出典にしない。

## 目的と責務

指定範囲のテスト方針・条件・ケースと、データ仕様・環境要件・準備・操作・後片付けを文書として具体化する。
共通戦略は横断原則、テーマ別戦略はその適用判断、テスト設計は条件・ケースと具体仕様を管理する。従来の「テスト方針」はテスト戦略として扱う。テーマ数・文書IDは適用規則で管理し、本スキルへ固定しない。
依頼と呼び出し元の権限を守り、保存先・ID・状態・正本・索引・参照方向は対象の適用規則から取得する。

- 受入条件と製品設計の契約を根拠とする。実装の現在の挙動だけから期待結果を決めず、新しい振る舞い・閾値・保証・受入条件を追加しない。
- 条件付き合意や未決の影響を分離して独立部分を続ける。ケース作成を上流合意・実行準備完了・試験合格にしない。
- 実データ生成・環境構築・試作・製品コード・テストコード・実行・製品結果評価は後続担当へ渡す。文書の構文・リンク確認は行える。
- 採番・対応・変更影響・引継ぎは[manage-product-documents](../manage-product-documents/SKILL.md)の該当操作を使う。保存形式は適用規則に従い、OKF指定時は[manage-okf](../manage-okf/SKILL.md)を使う。
- 全体設計の段階と戻り先は[design-productのワークフロー](../design-product/references/workflow.md)を正本とする。単独のテスト操作で製品設計全体や他操作を自動開始しない。

## 操作の選択

テスト設計全体は方針・分析・具体的設計・レビューを段階的に進める。既存の有効な入力は再作成せず、変更・再開は影響する条件・ケースと操作を選ぶ。
方針だけ・分析だけ・ケースだけ・レビューだけの依頼では該当手順だけを読み、不足と進められる範囲を返す。

| 必要な作業 | 参照する手順 |
| --- | --- |
| 共通・テーマ別テスト戦略の策定 | [テスト戦略](references/test-strategy.md) |
| テスト分析・条件整理 | [テスト分析](references/test-analysis.md) |
| ケース・データ仕様・環境要件・手順の設計 | [具体的なテスト設計](references/test-design.md) |
| テスト設計レビュー・完了判断 | [テスト設計レビュー](references/test-review.md) |

各手順から必要なテンプレートだけを読み、適用規則に合わせて例・不要な節を置換・削除する。
対象範囲・確認済み／未確認・未決・引継ぎ・次の作業を報告し、独立した進捗台帳は作らない。
