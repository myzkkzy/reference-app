# プロダクト着想エージェント

`product_ideation` は、あなたとのブレストとインタビューを通して、複数のアイデアと有望案の構想をまとめる担当です。何も決まっていない状態でも、持ち込み案がある状態でも使えます。

## 呼び出し方

このプロジェクトの新しいCodexセッションで、次のように依頼します。

> product_ideation エージェントを使って、プロダクトの着想を一緒に考えてください。まだ案はありません。興味や経験についてのインタビューと、アイデアの提案を交えながら進めてください。

持ち込み案や相談の再開にも対応します。

> product_ideation エージェントで、「……」という案を広げ、具体的な利用場面を考えてください。

> product_ideation エージェントで、docs/product-ideas/ の案とこれまでの判断理由を読み、保留していた案の検討を再開してください。

設定は [product_ideation.toml](../../.codex/agents/product_ideation.toml) です。モデル・権限は親から継承します。親がユーザーとの対話を仲介し、同じ担当へ回答を渡します。認識されない場合は、新規セッションとクライアントのカスタムエージェント対応・有効化設定を確認してください。[公式設定方式](https://learn.chatgpt.com/docs/agent-configuration/subagents)を使用します。

## 5つの対話の型

| 型 | 行うこと |
| --- | --- |
| 掘り起こす | 興味、経験、違和感、面倒なこと、実現したい体験を聞く |
| 広げる | 異なる切り口の案を基本3〜5件提示し、組み合わせや別の用途を考える |
| 深める | 想定利用者、使う場面、うれしい変化を具体的に描く |
| 比較する | 本人の関心、価値、独自性、試しやすさを言葉で比較する |
| まとめる | 有望案を構想文書にし、他の案や未決事項も残す |

固定の順序ではありません。ゼロからなら掘り起こし、持ち込み案なら深掘りから始められます。深めて別の可能性が見えたら広げ直し、比較してもピンと来なければ経験や興味に戻ります。途中の仮まとめも行い、各段階の承認や全段階の通過は要求しません。

質問は基本1〜2問、最大3問です。答えにくい場合は具体例や仮の案を提示します。質問だけを続けず、エージェントも発想を持ち寄ります。発散中に実現性・収益性だけで案を落とさず、比較段階で検討します。

## 成果物と検討状況

成果物は候補一覧と構想文書の2種類です。検討状況とは区別します。

```text
docs/product-ideas/
  index.md          # 候補一覧・検討状況・判断理由
  <idea-slug>.md    # 有望案などの詳細な構想
```

短い案は一覧だけに置き、有望案や詳細を残したい案を個別文書にします。実際の相談を始めるまで成果物ディレクトリは作りません。状況・判断理由は一覧、構想の詳細は個別文書を管理元とします。

| 検討状況 | 意味 |
| --- | --- |
| 検討中 | 発想を広げたり深めたりしている |
| 引継ぎ候補 | 有望案として選び、要求定義へ進めたい |
| 保留 | 判断材料が足りない、または今は取り組まない |
| 見送り | 理由を持って現時点では進めないと判断した |

新しい案は検討中とします。他の状態への変更はユーザーの選択に基づきます。保留・見送りも要約と理由を保存し、再検討できます。変更時は以前の判断と変更理由を残します。引継ぎ候補は開発決定や需要の実証を意味しません。

ユーザーの経験・意向、AIの提案・仮説、外部情報を区別します。市場・競合等を調べる場合は出典を残します。架空の利用場面を実際の顧客の声として扱いません。

## 要求定義との連携

着想 → [プロダクト要求定義](product-requirements.md) → [要件定義](requirements-definition.md)の順に担当をつなぎます。

「引継ぎ候補」のうち、ユーザーが要求定義へ進めると指定した案をインプットにします。状態だけで自動移行せず、既に移行指示があるなら確認を重ねません。

> product_requirements エージェントで、docs/product-ideas/ の引継ぎ候補「……」をインプットに要求定義を進めてください。構想の仮説と確認済みの情報を区別してください。

引継ぎには構想文書、選定理由、利用者・場面・価値、根拠、未確認の仮説、未決事項を含めます。構想文書に引継ぎの経緯と、作成された要求文書へのリンクを残します。検討状況は引継ぎ候補のままとし、要求の進捗・合意状況は要求文書で管理します。

要求定義で着想の再検討が必要になれば、この担当へ戻せます。着想担当は要求文書を直接変更しません。要求IDの採番、要件・設計・実装、外部顧客へのインタビュー実施、詳細な検証計画は担当外です。

## テンプレート

- [候補一覧](templates/product-ideation/idea-index.md)
- [構想文書](templates/product-ideation/idea.md)

必要な保存先に複製し、プレースホルダーを実際の内容に置き換えます。不明点は未確認・未決とし、不要な例示行は削除します。テンプレート自体を成果物として編集しません。

## 確認シナリオ

| 入力・状況 | 期待する対応 |
| --- | --- |
| 「何か作りたい」のみ | 興味や経験を少数の質問で聞き、異なる切り口の案を提案する |
| 既に案がある | 案を尊重して深掘りから始め、必要に応じて別の切り口を広げる |
| 「分からない」が続く | 同じ質問を繰り返さず、具体例や仮案への反応を聞く |
| 比較しても選べない | 複数案を維持し、保留や掘り起こしへの回帰を認める |
| AIが利用場面を描く | AIの仮説と明示し、顧客の発言や需要の実証にしない |
| AIが推奨しただけ | ユーザーが選択するまで検討中とし、引継ぎ候補にしない |
| 引継ぎ候補になっただけ | 要求定義を自動開始しない |
| 引継ぎ対象をユーザーが指定 | 構想と未確認の仮説を渡し、要求の合意済み扱いをしない |
| 保留・見送り案を再開 | 以前の判断理由を読んで再検討し、変更理由を残す |
| 要求定義から再検討を依頼 | 構想を見直して変更点を返し、要求文書は直接変更しない |

文書の指示による担当範囲とツールのアクセス制御は別です。実際の権限は親セッションに従います。
