# 要件定義エージェント

`requirements_definition` は、要求を検証可能な振る舞い・業務ルール・品質・制約と受入条件に具体化します。要求の作成・変更は [要求定義担当](product-requirements.md)、画面・API・DB・技術方式の設計と実装は後続担当の役割です。

## 利用方法

このプロジェクトの新規Codexセッションで次のように依頼します。

> requirements_definition エージェントを使って、docs/product-demands/ の対象要求を要件と受入条件に具体化してください。不明点は1〜3問ずつ確認し、影響する要件だけ保留してください。

変更時：

> requirements_definition エージェントで、変更された要求 DEM-xxx の影響を確認してください。関連要件と受入条件、対応表を更新し、要件IDを維持してください。

親が対話を仲介し、同じ担当に回答を引き継ぎます。要件担当は要求の不足・矛盾を親へ返し、独立した要件化を続けます。元の要求がない場合は要求定義への引継ぎから始めます。

設定は [requirements_definition.toml](../../.codex/agents/requirements_definition.toml) です。モデル・権限は親から継承します。認識されない場合はプロジェクトを開いた新規セッションとカスタムエージェントの有効化・対応状況を確認してください。[公式設定方式](https://learn.chatgpt.com/docs/agent-configuration/subagents)を使用しています。

## 要求・要件・設計の境界

| 区分 | 扱う内容 | 担当 |
| --- | --- | --- |
| 要求 | 誰が何に困り、なぜ、どの成果を望むか | product_requirements |
| 要件 | プロダクトの振る舞い・品質・制約と受入条件 | requirements_definition |
| 設計 | 画面レイアウト、API契約、DB構造、技術方式 | 後続担当 |

必要な情報は業務上の意味、外部連携は期待するやり取りとして記述します。業務の成功指標を機能の受入条件と混同しません。数値目標や業務ルールが不明なら未決とし、仮定を確定事項にしません。

## 文書と対応関係

要件本文の該当節へのリンクは、Markdown見出しから生成されるGitHub形式のアンカーを使った相対リンクとする。HTMLタグによる独自アンカーは埋め込まない。見出しを変更した場合は参照元のリンクも更新し、リンク先のファイルと見出しが存在することを確認する。

```text
docs/product-requirements/
  index.md
  cross-cutting.md
  <boundary>/
    index.md
    <topic>.md
```

要求側の境界を基本に、本文をテーマ単位に分割します。横断要件は一か所で管理し、境界から参照します。横断文書も大きくなれば `cross-cutting/` のテーマ文書に分割し、`cross-cutting.md` は索引にします。境界のない横断要求の対応表は分割先の関連テーマ文書で管理し、索引から参照します。実際の要件化を始めるまで空の成果物は作りません。

全体indexは横断要件を含む全要件の一覧・本文該当節への直接リンク・関連文書、境界indexは要件一覧・要求対応表・関連文書に限定します。一覧の列は「要件ID・要件名・短い説明・詳細」とし、詳細には本文該当節への相対リンクを記載します。関連文書は存在する参照先だけを掲載します。責務・対象範囲・対象外・未決事項・引継ぎなどの詳細はindexに記載しません。責務は本文の文脈、適用条件や未決事項は各要件本文、確認事項は「要求担当への確認」、引継ぎは「設計担当への引継ぎ」で管理します。

要求ID `DEM-xxx` と要件ID `REQ-001` 以降を区別し、多対多で対応付けます。要件本文に参照要求のリンク・内容の要約・合意状況を残し、境界の対応表に対象要求をすべて記載します。境界のない横断要求は横断文書の対応表で管理します。今回要件化しない対象外要求は、関連するテーマ別・横断文書の「要求担当への確認」にDEM-ID・相対リンク・除外理由を記載し、対応漏れと区別します。記録のために架空のREQ-IDは作りません。

対応表の要件化状況は「未着手・一部具体化・具体化済み・保留」。要件の合意状況は「ドラフト・条件付き合意・合意済み・保留・廃止」です。具体化済みでもユーザーの合意を意味しません。優先度は「必須・重要・将来候補・未決」で理由を添えます。

要件IDはプロジェクト全体で採番し、編集・移動で維持します。廃止IDは再利用せず、分割・統合では新旧IDの関係を該当要件本文に記載します。要求や要件の意味が変われば影響する要件をドラフトへ戻し、判断不能な箇所は保留にします。

「変更・合意の記録」の節・履歴表や代替の履歴文書は作成しません。現在の合意の根拠は各要件の「根拠・出典」に記載し、廃止した要件は合意状況を「廃止」にします。

## 合意状況と遷移

合意状況はREQ単位で管理し、実装完了・試験合格とは区別します。新規作成時はドラフトとします。

| 状態 | 意味 |
| --- | --- |
| ドラフト | 作成・修正中、または要件全体への合意待ち |
| 条件付き合意 | 確定部分と、未決事項を後続工程で決める条件に明示的な合意がある |
| 合意済み | 要件と受入条件に明示的な合意があり、対象範囲・合否判断を左右する未決事項がない |
| 保留 | 要求の矛盾・不足などにより判断を進められない |
| 廃止 | 明示的な判断により適用を終了した。IDは再利用しない |

| 遷移 | 条件 |
| --- | --- |
| 新規 → ドラフト | 要件案を作成する |
| ドラフト → 合意済み | 本文・受入条件・優先度を含む要件全体への明示的な合意があり、重大な未決事項がなく受入条件が検証可能 |
| ドラフト → 条件付き合意 | 確定部分、残る条件、引継ぎ先、確定時期、解消条件、進めてよい範囲に明示的な合意がある |
| 条件付き合意 → 合意済み | 条件を解消し、確定した内容への明示的な合意を得る |
| ドラフト・条件付き合意・合意済み → 保留 | 根拠となる要求の矛盾などで判断不能になる |
| 保留 → ドラフト | 保留理由が解消し、要件を再確認できる |
| 条件付き合意・合意済み → ドラフト | 要件の意味・適用範囲・受入条件が変更される |
| 廃止以外 → 廃止 | 適用終了が明示的に決定される |

誤字・リンク修正では状態を戻しません。依存先の変更は影響する要件だけに反映し、未決部分に影響されない要件の状態は維持します。廃止要件の再導入には新IDを採番し、元IDとの関係を本文に記載します。

設計方式や具体的な試験操作だけが残り、期待結果と選定方針が確定している場合は合意済みにできます。対象範囲・合否を左右する条件が残る場合は条件付き合意とし、要求の矛盾や不足は保留にします。条件付き合意では合意した範囲の設計・試作を進め、未確定部分の最終的な受入判定は条件の確定と合意後に行います。

合意確認では対象REQ、現行本文・受入条件・優先度と残る条件を提示します。個別回答、スキップの選択、計画採用・文書反映の指示だけで要件全体への合意を推定しません。既に対象範囲への明示的な合意があれば再確認は不要です。合意が得られたREQだけ状態を遷移させます。

「根拠・出典」に現在の合意日・合意者・対象範囲・回答根拠を記載し、「未決事項」に残る条件・影響・引継ぎ先・確定時期・解消条件・進めてよい範囲を記載します。本文、文脈の説明、設計担当への引継ぎ表を同期します。要求対応表の要件化状況は別管理とし、履歴文書は追加しません。

## 受入条件と引継ぎ

- 機能要件：ケース、前提、操作・事象、期待結果。ケース区分は「正常」「異常」のみとする。正常は仕様で認めた操作・利用が成立する場合、異常は入力不備・処理失敗などへの対応を確認する場合とする。境界値・権限不足・回復などの観点は前提、操作・事象、期待結果に記載し、異常からの回復を確認するケースは「異常」に分類する。
- 非機能要件：評価条件、基準、検証方法。閾値や測定条件が不明な部分は未決です。
- 制約：遵守を判定する条件と確認方法を記録します。

要求の不足・矛盾・未合意に依存する要件は保留し、親へ対象要求・根拠・影響・確認事項を返します。独立した要件はドラフト化します。新しい要求が必要なら要求担当への差戻し事項にし、要求文書を直接変更しません。

設計担当への引継ぎには文書リンク、要件ID、参照要求、受入条件、合意状況、未決事項、設計上の検討事項を含めます。技術方式の候補を設計上の確定事項として扱いません。

## 確認シナリオ

| 状況 | 期待する動作 |
| --- | --- |
| 合意済み要求から機能を具体化 | 受入条件のケースを「正常」「異常」に分類し、関連する異常時の対応も扱い、DEM-IDと関連付ける |
| 性能目標の閾値が未指定 | 数値を捏造せず、評価条件・基準の質問を返す |
| 一部の要求が矛盾 | 関連要件だけ保留し、独立した要件はドラフト化する |
| 元の要求が変更 | 依存要件・受入条件・対応表を確認し、影響する状態を戻す |
| 複数境界に共通する要件 | 横断文書に本文を置き、各境界から同じREQ-IDを参照する |
| 対象要求に対応要件がない | 未着手・保留を明示し、対応漏れとしてレビューする |
| 要件の根拠となる要求がない | 要求担当へ差し戻し、架空のDEM-IDを付けない |
| indexの更新 | 全体は全要件の一覧と参照先、境界は要件一覧・要求対応表と参照先に限定する |
| 今回要件化しない要求がある | 関連本文の「要求担当への確認」にDEM-ID・リンク・除外理由を記載し、REQ-IDを作らない |
| 要件の変更・合意 | 本文と現在の合意状況・根拠を更新し、履歴の節・表や代替文書を作らない |
| 要件の分割・統合・廃止 | 新旧ID関係を該当本文に記載し、廃止状態を明示してIDを再利用しない |
| 横断文書の分割 | 境界のない要求の対応表を関連テーマ文書で管理し、索引から参照する |

文書の指示による担当範囲と、ツールのアクセス制御は別です。実際の権限は親セッションに従います。
