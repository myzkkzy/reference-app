# 要件定義エージェント

`requirements_definition` は、要求を検証可能な振る舞い・業務ルール・品質・制約と受入条件に具体化します。要求の作成・変更は [要求定義担当](product-requirements.md)、画面・API・DB・技術方式の設計と実装は後続担当の役割です。

## 利用方法

このプロジェクトの新規Codexセッションで次のように依頼します。

> requirements_definition エージェントを使って、docs/product-demands/ の対象要求を要件と受入条件に具体化してください。不明点は1〜3問ずつ確認し、影響する要件だけ保留してください。

変更時：

> requirements_definition エージェントで、変更された要求 DEM-xxx の影響を確認してください。関連要件と受入条件、対応表を更新し、要件IDを維持してください。

親が対話を仲介し、同じ担当に回答を引き継ぎます。要件担当は要求の不足・矛盾を親へ返し、独立した要件化を続けます。元の要求がない場合は要求定義への引継ぎから始めます。

設定は [requirements_definition.toml](../../.codex/agents/requirements_definition.toml) です。モデル・権限は親から継承します。認識されない場合はプロジェクトを開いた新規セッションとカスタムエージェントの有効化・対応状況を確認してください。[公式設定方式](https://learn.chatgpt.com/docs/agent-configuration/subagents)を使用しています。

## 要求・要件・設計の境界

| 区分 | 扱う内容 | 担当 |
| --- | --- | --- |
| 要求 | 誰が何に困り、なぜ、どの成果を望むか | product_requirements |
| 要件 | プロダクトの振る舞い・品質・制約と受入条件 | requirements_definition |
| 設計 | 画面レイアウト、API契約、DB構造、技術方式 | 後続担当 |

必要な情報は業務上の意味、外部連携は期待するやり取りとして記述します。業務の成功指標を機能の受入条件と混同しません。数値目標や業務ルールが不明なら未決とし、仮定を確定事項にしません。

## 文書と対応関係

```text
docs/product-requirements/
  index.md
  cross-cutting.md
  <boundary>/
    index.md
    <topic>.md
```

要求側の境界を基本に、本文をテーマ単位に分割します。横断要件は一か所で管理し、境界から参照します。横断文書も大きくなれば `cross-cutting/` のテーマ文書に分割し、`cross-cutting.md` は索引にします。実際の要件化を始めるまで空の成果物は作りません。

要求ID `DEM-xxx` と要件ID `REQ-001` 以降を区別し、多対多で対応付けます。要件本文に参照要求のリンク・内容の要約・合意状況を残し、境界の対応表に対象要求をすべて記載します。境界のない横断要求は横断文書の対応表で管理します。対象外は全体indexに理由を記録します。

対応表の要件化状況は「未着手・一部具体化・具体化済み・保留」。要件の合意状況は「ドラフト・合意済み・保留・廃止」です。具体化済みでもユーザーの合意を意味しません。優先度は「必須・重要・将来候補・未決」で理由を添えます。

要件IDはプロジェクト全体で採番し、編集・移動で維持します。廃止IDは再利用せず、分割・統合では新旧IDを記録します。要求や要件の意味が変われば影響する要件をドラフトへ戻し、判断不能な箇所は保留にします。

## 受入条件と引継ぎ

- 機能要件：前提、操作・事象、期待結果。関連する正常・例外・権限不足・境界値を扱います。
- 非機能要件：評価条件、基準、検証方法。閾値や測定条件が不明な部分は未決です。
- 制約：遵守を判定する条件と確認方法を記録します。

要求の不足・矛盾・未合意に依存する要件は保留し、親へ対象要求・根拠・影響・確認事項を返します。独立した要件はドラフト化します。新しい要求が必要なら要求担当への差戻し事項にし、要求文書を直接変更しません。

設計担当への引継ぎには文書リンク、要件ID、参照要求、受入条件、合意状況、未決事項、設計上の検討事項を含めます。技術方式の候補を設計上の確定事項として扱いません。

## 確認シナリオ

| 状況 | 期待する動作 |
| --- | --- |
| 合意済み要求から機能を具体化 | 正常・関連する例外を受入条件にし、DEM-IDと関連付ける |
| 性能目標の閾値が未指定 | 数値を捏造せず、評価条件・基準の質問を返す |
| 一部の要求が矛盾 | 関連要件だけ保留し、独立した要件はドラフト化する |
| 元の要求が変更 | 依存要件・受入条件・対応表を確認し、影響する状態を戻す |
| 複数境界に共通する要件 | 横断文書に本文を置き、各境界から同じREQ-IDを参照する |
| 対象要求に対応要件がない | 未着手・保留を明示し、対応漏れとしてレビューする |
| 要件の根拠となる要求がない | 要求担当へ差し戻し、架空のDEM-IDを付けない |

文書の指示による担当範囲と、ツールのアクセス制御は別です。実際の権限は親セッションに従います。
