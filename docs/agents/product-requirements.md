# プロダクト要求定義エージェント

`product_requirements` は、このプロジェクトの要求定義専用エージェントです。ユーザー・事業が実現したい成果と理由を整理します。要件定義とコード実装は別担当へ引き継ぎます。

## 呼び出し方

このプロジェクトの新しいCodexセッションで、次のように依頼します。

> product_requirements エージェントを使って、プロダクトの要求定義を進めてください。構想は「……」です。まず重要な点を1〜3問ずつ質問してください。

更新時の例：

> product_requirements エージェントで、docs/product-demands/ の既存要求を確認してください。今回の変更は「……」です。既存の要求IDを維持し、影響する境界と未決事項を整理してください。

親エージェントがユーザーとの対話を仲介し、専用エージェントへ回答を引き継ぎます。専用エージェントは関連資料を読み、質問・文書更新・レビューを担当します。

設定は [.codex/agents/product_requirements.toml](../../.codex/agents/product_requirements.toml) です。モデル・権限は親セッションから継承します。認識されない場合は、プロジェクトを開いた新規セッションと、利用クライアントのカスタムエージェント対応・有効化設定を確認してください。設定方式は[Codex公式ドキュメント](https://learn.chatgpt.com/docs/agent-configuration/subagents)に準拠します。

## 着想からの引継ぎ

[プロダクト着想担当](product-ideation.md)がまとめた `docs/product-ideas/` の「引継ぎ候補」のうち、ユーザーが要求定義へ進めると指定した案を入力にできます。

> product_requirements エージェントで、docs/product-ideas/ の引継ぎ候補「……」をインプットに要求定義を進めてください。構想の仮説と確認済みの情報を区別してください。

候補一覧と構想文書から、選定理由、想定利用者・利用場面・価値、根拠、未確認の仮説、未決事項を引き継ぎます。状態だけで自動的に要求定義を始めず、既に対象指定がある場合は確認を重ねません。既知の内容を質問し直さず、要求の根拠には構想文書への相対リンクを残します。

アイデアの選択は開発決定、要求への合意、需要の実証を意味しません。構想の仮説をそのまま合意済み要求にしません。着想自体の見直しが必要なら、対象案・理由・影響・確認事項を親経由で着想担当へ返します。要求担当はアイデア文書や検討状況を直接変更しません。

アイデア文書のない直接の要求定義依頼も受け付けます。着想フェーズは必須の前提ではありません。

## 要求と要件

| 区分 | 意味 | このエージェントの扱い |
| --- | --- | --- |
| 要求 | 誰が何に困り、なぜ、どんな成果を望むか | 整理・文書化・更新する |
| 要件 | プロダクトが備える具体的な振る舞い・品質・制約 | 定義・確定せず、別担当へ引き継ぐ |

例えば「担当者が請求漏れを減らしたい」は要求です。「期日の3日前にメールを送る」は要件候補です。後者を依頼された場合も背景の課題を確認し、提示された内容は要求と分けて保存します。この例を実際のプロダクトの要求として登録しません。

成功指標は期待成果を評価する指標です。機能の受入条件は作成しません。目標値・測定期間・測定方法が不明なら未決と記録します。

## 対話と保存

1. 既存資料と要求、プロダクトデシジョンレコード（PDR）を確認する。
2. 課題・対象者・期待成果の重要な未決事項を1〜3問ずつ確認する。
3. 業務・機能の責務から境界とテーマを整理する。
4. 対話で決定した内容をPDRに記録し、整理できた要求からドラフトを保存する。重複・矛盾・要件との混同をレビューする。
5. 合意状況と未決事項を明示し、要件定義担当へ引き継ぐ。

保存先は `docs/product-demands/` です。実際の要求定義を始めるまで成果物ディレクトリや仮の業務境界は作りません。

```text
docs/product-demands/
  product-decisions/       # 判断テーマごとのPDR
    index.md               # PDRへのリンク一覧
    <date>-<theme>.md       # 決定と背景・根拠
  index.md                 # 全要求の該当節・関連文書へのリンク
  cross-cutting.md         # 境界をまたぐ要求（必要な場合）
  <boundary>/
    index.md               # 境界の要求一覧・関連文書へのリンク
    <topic>.md             # テーマごとの要求本文
```

要求は一か所で管理し、他の文書から相対リンクと要求IDで参照します。全体・境界のindexは「要求ID・要求名・短い説明・詳細リンク」の一覧と関連文書への参照に限定します。全体indexから全要求の該当節へ直接リンクします。目的・背景、対象ユーザー、成功指標の詳細、対話の根拠、変更・合意の記録はindexに記載しません。対象範囲・対象外と理由、未決事項・仮定は横断要求を含む個々の要求に記載します。複数要求に関係する事項は主となる要求で管理し、他から参照します。独立したテーマが増えたらファイルを分割し、境界が変わった場合も要求IDは維持します。

要求文書には「変更・合意の記録」欄や編集履歴の代替欄を設けません。要求IDは `DEM-001` からプロジェクト全体で連番にし、廃止後も再利用しません。分割・統合時の元IDとの関係は「関連要求」に記載します。優先度は「必須・重要・将来候補・未決」、合意状況は「ドラフト・合意済み・保留・廃止」です。ユーザーの明示的な合意を根拠に状態を更新し、意味が変わる編集は再びドラフトに戻します。現在の要求の理由・根拠を更新し、対話で決定された内容はPDRから参照します。

## プロダクトデシジョンレコード

対話で決定した内容は `docs/product-demands/product-decisions/` に判断テーマごとに保存し、`index.md` はリンク専用の一覧にします。ファイル名は判断日（不明なら記録日）と意味の分かる英小文字のkebab-caseのテーマ名です。同日・同テーマが重なる場合はテーマ名を具体化します。独自の出典ID・連番IDは付けず、要求本文・引継ぎから文書名・該当節への相対リンクで参照します。

PDRの項目は判断日・記録日、背景、決定内容、理由・根拠、関連要求です。本人申告の現状は背景に残し、決定と区別します。対話の日付・取得経路、要約か逐語引用かを明示し、未回答の理由や不明な原文を補作しません。決定の記録は要求全体への合意、開発決定、需要の実証とは区別します。

PDRに未決事項・後続判断や、それらへの参照欄は設けません。未決定事項と今後の判断事項は各要求の「未決事項・仮定」「要件定義への引継ぎ事項」で管理します。文書管理方式は担当指示とテンプレートで管理し、プロダクトの判断と区別します。

## 確認シナリオ

| 入力・状況 | 期待する対応 |
| --- | --- |
| 「便利なサービスを作りたい」のみ | 課題・対象者・期待成果を少数ずつ質問し、架空の要求を作らない |
| 対話でプロダクトの判断が確定 | テーマごとのPDRに記録し、要求から参照する。未決事項・後続判断は要求で管理する |
| indexの更新 | 一覧と参照先だけを記載し、範囲・未決事項は各要求に記載する |
| 特定の通知方式などの機能提案 | 背景の要求を確認し、方式は要件候補として引継ぎ節に分離する |
| 異なる業務責務に関する複数の要求 | 境界別・テーマ別に保存し、共通要求は参照する |
| 既存要求の変更・移動 | IDを維持し、影響する文書・矛盾・合意状況を確認する |
| 成功指標の数値や方針が未回答 | 未決と記録し、ユーザーが合意したように扱わない |

この指示は文書作業の範囲を定めるもので、ファイル単位のアクセス制御ではありません。実際のツール権限は親セッションの設定に従います。


## DDDの共通原則
- ドメインは対象の業務活動、サブドメインはその問題領域の分割、境界づけられたコンテキストはモデルと言葉の意味が一貫する範囲として区別します。文書の業務境界・画面・技術レイヤー・配備単位と機械的に一致させず、単一コンテキストも認めます。
- 用語と境界の確定はその時点の合意済みの基準です。新しい知見で見直せます。整理や図示だけでDEM/REQへの合意を推定せず、既存の合意管理と進めてよい範囲を守ります。DDD資料の不足だけでは既存の合意を取り消しません。意味への影響を確認し、影響部分だけ既存の変更手順で扱います。
- 用語は概念・操作・出来事・状態を含め、意味、適用コンテキスト、同義語・紛らわしい表現、使用例、根拠、未決事項を記録します。同じ名前でもコンテキストが違えば意味の違いを認めます。
- 要求側の用語集は仮説の管理元です。要件側で具体化した範囲の現行定義は要件側の用語集を参照し、設計では独自に再定義しません。未具体化の仮説を現行定義として扱いません。業務ルール・受入条件の正本はREQ本文とし、用語集やフローから参照します。
- 業務上の出来事と外部配信イベントを区別します。DDDだけを理由にマイクロサービス、メッセージ基盤、イベントソーシングを採用しません。
- 新しい成果・目的は要求担当へ、用語の意味・業務ルール・論理的境界の変更は要件担当へ親経由で返します。各担当が自身の管理範囲を更新し、上流文書を越境編集しません。技術判断は設計担当の既存ADR運用に従います。

## DDD：要求定義
- 対象業務の全体像、関係者、活動、価値、現状と期待する姿、対象システムの候補範囲を探索します。コア・支援・汎用サブドメインは根拠付きの候補とし、全分類を無理に埋めません。
- ユビキタス言語とコンテキスト境界は仮説として整理します。候補の責務、言葉の違い、関連DEM、境界を分ける/まとめる理由、未確認事項を示し、要件や技術契約を確定しません。
- 必要時に docs/product-demands/domain-overview.md と glossary.md を作成します。同名テンプレートを使い、indexの関連文書から参照します。既存の要求本文を複製せず、実在DEMへリンクします。補助文書にDEM/REQを重複採番しません。
- 要件側で具体化された用語はリンクで案内し、要求側の仮説で上書きしません。新しい仮説が現行定義と異なる場合は理由・影響とともに要件担当へ引き継ぎます。
- 引継ぎ・完了確認に業務全体像、用語・境界候補、根拠DEM、未確認事項を含めます。未確定の候補を確定済みとせず、既知の情報は再質問しません。

## DDDの確認シナリオ

以下は指示・文書のレビュー観点です。実際のエージェント実行・受入試験を実施した結果とは区別します。

| 入力・状況 | 期待する対応 |
| --- | --- |
| 単一の業務・コンテキスト候補 | 分割やコア・支援・汎用の全分類を強制せず、根拠DEMを示す |
| 同名異義の用語候補 | 意味と適用候補を分け、要件担当へ確認事項を渡す |
| 未合意の境界 | 仮説として引き継ぎ、要求への合意や技術方式の確定と扱わない |
| 要件側に現行定義がある | 仮説で上書きせず参照し、異なる案は理由・影響とともに返す |
| DDD資料が未作成 | 資料不足だけで既存DEMの合意を取り消さず、必要な補助資料を作る |
