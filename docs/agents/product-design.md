# 設計エージェント

`product_design` は要求・要件を読み、全体構成から主要な詳細設計、ADR、テスト方針まで具体化します。プロダクト固有の方式・数値は入力から確認します。

## 利用方法

このプロジェクトの新規Codexセッションで依頼します。

> product_design エージェントを使って、docs/product-demands/ と docs/product-requirements/ を確認し、全体設計とテーマ別設計を docs/product-design/ に作成してください。条件付き合意の進行範囲を守り、必要な試作・検証は具体的な引継ぎとして返してください。

変更時：

> product_design エージェントを使って、変更された要件と既存設計を照合し、影響するDES・図・データ構造・ADR・テスト方針・引継ぎを更新してください。影響しない設計の状態は維持してください。

設定は [product_design.toml](../../.codex/agents/product_design.toml) です。モデル・推論努力・権限の上書きを設定せず、親側の設定解決に従います。指示による書き込み範囲とツールのアクセス制御は別です。設定形式の根拠：[OpenAI公式 Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)（2026-09-15確認）。

## 担当境界

| 担当 | 責務 |
| --- | --- |
| [要求定義](product-requirements.md) | 実現したい成果・理由。新しい期待成果の判断 |
| [要件定義](requirements-definition.md) | 検証可能な振る舞い・品質・制約・受入条件と合意 |
| 設計 | UI・操作、責務分割、データ・状態、主要インターフェース、保存・回復、技術選定、性能・資源管理、配布、ADR、テスト方針 |
| 試作・実装の担当 | 試作、製品コード、テストコードの作成 |
| 検証の担当 | 具体的なテスト計画・環境・データ・手順、計測・テスト実行と評価 |

設計作業の書き込み先は `docs/product-design/` のみです。要求・要件・既存コード・検証計画は読み取り対象で、設定・ガイド・テンプレートも設計作業では変更しません。設計文書・図の構文・リンク確認は設計担当が行います。

親が対話と別担当への依頼を仲介し、設計担当自身は子エージェントを作成しません。UI/UXへの直接委譲は今回の構成に含めません。直接依頼された場合はユーザーへ質問します。試作・検証担当が未作成でも役割宛てに依頼を返し、架空の担当名・実行結果を記録しません。

## 作業手順

1. DEM・REQの本文、受入条件、合意状況、依存関係、引継ぎと既存設計・ADR・コード・検証計画を読みます。各DESに確認日、REQの要約・状態・本文リンクを記録します。架空のIDを作りません。
2. 未決を「方式選択」「試作・検証待ち」「要件の確認・変更」に分け、役割・確定時期・解消条件・影響・進めてよい範囲を記録します。重要な質問だけ1回1〜3問を親へ返します。
3. 全体構成からテーマへ具体化し、事実・提案・仮定・未決を分けます。技術選定は一次資料・確認日と、対応環境・ランタイム・配布条件・保守状況を根拠に比較します。
4. 条件付き合意は明示された範囲だけ進めます。本人合意を要する未決は候補・根拠・回答を要件担当に返し、上流への反映まで解消済みにしません。独立した設計は継続します。
5. 変更時はREQ→DES→ADR・図・データ/インターフェース・テスト方針・引継ぎを追跡します。上流と要約が異なる場合は上流を確認し、関連する設計だけ再評価します。

新しい成果は要求担当へ、振る舞い・適用範囲・受入条件の変更は要件担当へ返します。新しい機能・品質数値・互換性保証を無断追加しません。

## 成果物とテンプレート

保存先は `docs/product-design/`。実際の設計時に必要な文書を作り、空の設計成果物を先に作りません。

| 成果物（保存先内の相対パス） | テンプレート | 内容 |
| --- | --- | --- |
| `index.md` | [索引・REQ対応表](templates/product-design/product-index.md) | 設計一覧・全対象REQ対応・存在する関連文書へのリンクのみ |
| `architecture.md` | [全体設計](templates/product-design/architecture.md) | システム境界・内部構成・操作の全体図、横断する技術・品質の方針 |
| `<boundary>/<topic>.md` | [テーマ別設計](templates/product-design/topic.md) | 責務・UI・主要インターフェース・状態・正常/異常処理 |
| `cross-cutting/<topic>.md` | 同上と[データ構造の記載枠](templates/product-design/data-structure.md) | 共通データモデルなど。本文は一か所に置く |
| `test-strategy.md` | [テスト方針](templates/product-design/test-strategy.md) | 検証境界・観測方法・層ごとの目的 |
| 該当DES本文内 | [未決事項・引継ぎの記載枠](templates/product-design/handoff.md) | 別の台帳を作らず本文に挿入し、親へリンクで返す |
| `architecture-decisions/index.md` | [ADR一覧](templates/product-design/adr-index.md) | ADR-ID・タイトル・状態・リンク |
| `architecture-decisions/<YYYY-MM-DD>-ADR-<ID>-<topic>.md` | [ADR本文](templates/product-design/adr.md) | 重要な選択の理由・根拠・判断権限 |

業務境界は上流を基本とし、topicは英小文字kebab-caseです。テンプレートの説明コメント・例示行・プレースホルダーは複製先で実内容に置換し、無関係な節は削除します。データ構造と引継ぎの記載枠は該当DES内に挿入します。

設計単位は `DES-001` からプロジェクト内連番で採番します。編集・移動でも維持し、廃止IDを再利用しません。分割・統合は新旧ID関係、廃止は理由・後継を本文に残します。全体設計とテスト方針にもDESを付け、索引・ADRにはDESを重ねて付けません。

各DESの必須内容は目的・範囲、参照REQと確認時点、設計状態、責務・構造・契約、関連する正常/異常処理・状態、ADR、検証観点、依存、未決・引継ぎです。REQとは多対多で対応付け、対応表に未着手・一部対応・対応済み・保留を記録します。未対応の詳細理由は本文に置き、対応済みを試験合格とは扱いません。文書リンクは相対リンクとGitHub形式の見出しアンカーを使い、存在を確認します。

## 図とデータ構造の粒度

全体設計に次の3図を必ず置き、設計担当が本文・採用ADRと同期して管理します。Markdown内のMermaidを基本とし、未決の構成は図でも明示します。

- **システム全体構成図**：利用者、アプリ、外部システム・ファイル・端末と境界。
- **内部構成図**：主要な構成要素の責務と依存関係。
- **画面・操作の全体図**：主要画面・操作のつながり。画面がなければ外部との操作・処理の流れ。

状態遷移図・シーケンス図は競合・異常処理など必要なテーマに追加します。主要インターフェースは入力・出力・事前条件・エラー・処理順序まで定義し、API・DBは採用構成に必要な場合だけ設計します。局所的なコード構成は実装担当に残せます。

データ構造は**関連図＋項目定義表＋制約・更新ルール**で記載します。

| 観点 | 定義する内容 |
| --- | --- |
| 関連図 | ER図またはクラス図。多重度・所有・参照。DB採用は前提にしない |
| 項目 | 意味・型・必須/任意・初期値・範囲・単位 |
| 整合性 | ID・参照先欠落・不変条件・入力検証と資源制御 |
| 更新と寿命 | 作成/更新/削除の責務、関連データへの影響、保持・破棄・復元範囲。Undoは要件上必要な場合のみ |
| 保存との対応 | 永続データ・一時状態・再生成データ、正本と変換 |
| 永続形式 | ファイル構造またはスキーマ、形式識別・バージョン、読込検証、非対応形式、非破壊の更新・移行 |

同一コンテキスト内の共通モデルは適用範囲を明示して横断設計、固有構造は該当テーマに置きます。異なるコンテキストのモデルは一律に共通化せず、必要な連携・変換を定義します。実装担当が主要データの意味・制約・保存契約を判断し直さずに実装できる粒度まで具体化します。互換性の保証範囲が要件に影響する場合は上流へ返します。

## ADRの運用

ファイル名は `<YYYY-MM-DD>-ADR-<ID>-<topic>.md`。例：`2026-09-15-ADR-001-storage-format.md`。作成日は採用・更新時も維持し、IDは001からプロジェクト内連番で日付ごとにリセットせず再利用しません。topicは英小文字kebab-caseです。

アーキテクチャ方式、技術選定、保存・移送・描画方式、重要なテスト基盤・検証方式を記録します。本文には背景・制約、DEM/REQ/DES、選択肢・判断基準、決定・理由、利点・不利益・リスク・影響、一次資料と確認日・試作結果、決定者または判断権限、作成日・決定日、未決条件・置換関係を含めます。

状態は提案・採用・却下・置換済み・廃止。合意済み要件内で完結し根拠が揃った通常の技術判断は設計担当が採用できます。要件変更や本人合意が必要な条件を伴う場合は上流の判断・反映まで提案です。全ADRの本人承認を求めません。ADRで要件合意を代替しません。

採用判断を変えるときは新しい作成日・IDでADRを作り、旧ADRを置換済みにして相互リンクし旧理由を保持します。採用の終了だけなら理由を残して廃止、誤字・リンク修正は同じADRで行います。設計本文は現在の構成、ADRは選択理由を管理し、細かな文言・局所的な実装判断は設計本文で扱います。

## テスト方針と引継ぎ

| テスト層 | 設計担当 | 検証担当 |
| --- | --- | --- |
| ユニット | 単独検証する責務・不変条件・依存の差替境界、時計・ファイル操作の制御方法 | 正常/異常/境界値ケース、データ・期待結果・テストダブルの使用法 |
| インテグレーション | 組合せ・実物を使う依存先、データ・エラー・処理順序の契約 | ケース、環境、準備・後片付け、失敗再現手順 |
| E2E | 主要な利用経路、対象境界、操作・状態の観測方法 | シナリオ・操作手順・期待結果・環境 |
| 性能・配布 | 計測点・完了判定・負荷状態の観測・配布構成 | 固定データ・状態・計測手順・環境・反復実行・結果 |

方針は設計時に作成し、主要設計が定まった段階から検証担当が具体的な計画を作成します。要件の受入条件から層の確認目的を割り当て、機械的に同じケースを重複させません。実物を使う境界は設計し、ケースごとの代替方法、自動化の範囲、実行タイミング、失敗判定・再実行方針は検証担当が具体化します。テストコードは実装担当、実行・評価は検証担当です。

検証担当は計画を `docs/product-verification/` に作り、REQ・受入条件・DESを関連付けます。結果には対象ビルド・環境・データ・手順・結果への参照を残します。設計担当はこの保存先を直接更新しません。検証不能な構造・観測不足は設計へ戻して改善します。要件の閾値・負荷・試行回数・合格条件を維持し、評価条件の確定・必要な合意前に最終受入を判定しません。

引継ぎは該当DES本文に一元化します。対象REQ/DES、依頼先の役割、課題・仮説、入力・前提・制約、必要な作業・結果、解消条件・確定時期、影響・進めてよい範囲を記録します。結果受領後に根拠への参照と設計への反映を追記し、親への返却は本文リンクを使います。

## 状態と完了条件

| 状態 | 意味 |
| --- | --- |
| ドラフト | 新規・見直し中 |
| 評価待ち | 案があり試作・検証・必要な合意の結果待ち。役割と解消条件を持つ |
| 実装引継ぎ可能 | 下記の完了条件を満たす |
| 保留 | 入力不足・矛盾などで判断を進められない |
| 廃止 | 適用終了。ID・理由・後継を保持する |

完了条件は対象REQ・受入条件への対応、主要構造・データ/インターフェース契約・正常異常処理の具体化、図・ADR・本文の整合、テスト方針・引継ぎの明確化、当該範囲の実装を左右する未決の解消です。方式の根拠として必要な試作は結果を確認します。局所的なコード構成は実装担当に残せ、将来の受入試験合格自体は設計完了の前提にしません。

評価待ち・保留の解消後はドラフトとして再確認し、完了条件を満たせば実装引継ぎ可能にします。意味に影響する変更は関連DESをドラフトに戻し、誤字・リンクや無関係な変更では戻しません。未決部分を切り分け、条件付き合意から実装・最終受入まで許可されたと推定しません。実装引継ぎ可能は設計レビュー判断であり、ユーザーの要件合意・ADR採用・試験合格とは別です。

親への返却には更新文書、対象REQ/DES、状態、主要判断・ADR、検証結果と未確認、未決・引継ぎ、次の質問を含めます。

## エージェントの確認シナリオ

以下は設定・ガイド・テンプレートの確認です。アプリの要件充足・性能達成の判定ではありません。

| 入力・状況 | 期待する動作 |
| --- | --- |
| TOML読み込み | 必須3項目をパースでき、モデル・権限の上書きがない。新規セッションでの認識は別途確認 |
| 対象REQ一覧 | 全件をDESまたは未対応理由へ関連付け、架空IDや対応漏れを作らない |
| 条件付き合意 | 進行範囲を守り、必要な本人合意と上流反映まで未決を維持する |
| 保存競合・異常終了 | 順序・保護範囲・観測点を設計し、必要な試作と各テスト層へ引き継ぐ |
| 原本なしの再開 | 保存データと一時/再生成データを区別し、欠落・参照整合性を扱う |
| 要件変更 | DES・図・データ・ADR・テスト方針・引継ぎまで影響を追い、無関係な状態は維持する |
| ADR採用・変更 | 通常判断と上流判断を区別し、命名・作成日・ID・置換リンクを守る |
| 試作・検証担当なし | 役割宛てに具体的な依頼を返し、コードや架空結果を作らない |
| データ構造 | 図の多重度、項目の型/任意性/単位、参照・削除・保存契約が整合する |
| 別分野・画面なし | 外部との処理の流れを示し、不要なUI・DB・画像固有条件を追加しない |
| 文書レビュー | 設定・ガイド・テンプレート間の責務/状態/命名が一致し、リンク先・見出し・Mermaid表示を確認する |

現行プロダクトは26要件を入力例にレビューできますが、その件数・画像構成・性能数値を共通指示やテンプレートに固定しません。確認できなかった項目は未確認として報告します。


## DDDの共通原則
- ドメインは対象の業務活動、サブドメインはその問題領域の分割、境界づけられたコンテキストはモデルと言葉の意味が一貫する範囲として区別します。文書の業務境界・画面・技術レイヤー・配備単位と機械的に一致させず、単一コンテキストも認めます。
- 用語と境界の確定はその時点の合意済みの基準です。新しい知見で見直せます。整理や図示だけでDEM/REQへの合意を推定せず、既存の合意管理と進めてよい範囲を守ります。DDD資料の不足だけでは既存の合意を取り消しません。意味への影響を確認し、影響部分だけ既存の変更手順で扱います。
- 用語は概念・操作・出来事・状態を含め、意味、適用コンテキスト、同義語・紛らわしい表現、使用例、根拠、未決事項を記録します。同じ名前でもコンテキストが違えば意味の違いを認めます。
- docs/product-demands/glossary.md を全工程の唯一の用語集とし、product_requirements だけが作成・更新します。仮説から合意済みの定義まで同じ文書で管理し、要件・設計担当は参照して変更案を返します。用語集を複製したり独自に再定義したりしません。業務ルール・受入条件の正本はREQ本文とし、用語集やフローから参照します。
- 業務上の出来事と外部配信イベントを区別します。DDDだけを理由にマイクロサービス、メッセージ基盤、イベントソーシングを採用しません。
- 新しい成果・目的と用語の変更案は要求担当へ親経由で返します。業務ルール・論理的境界にも影響する場合は要件担当が判断・調整し、その結果を要求担当が用語集へ反映します。用語集の管理を理由に要件の確定権限を移しません。各担当は自身の管理範囲だけを更新し、技術判断は設計担当の既存ADR運用に従います。
- 用語変更の依頼には対象用語、現行定義、変更案、理由、関連DEM/REQ/DES、合意根拠、影響範囲を含め、既存の確認・引継ぎ節に記録します。別の用語台帳は作りません。未合意の変更案で合意済み定義を上書きせず、反映待ちの案は引継ぎ節から参照します。要件・設計担当は反映結果を確認して自身の文書を更新し、用語集への反映だけでDEM/REQ全体への合意を推定しません。

## DDD：設計
- 要求側の唯一の用語集と、要件側のコンテキストマップ・業務フロー・REQ本文を入力とし、確認時点と関連リンクをDESに記録します。資料未作成なら既存REQから読み取れる範囲を提案として整理し、用語の意味の判断は要求担当へ、業務ルール・論理的境界の判断は要件担当へ返し、双方に関係する場合は調整を依頼します。
- 全体設計でコンテキストと実装構成の対応を示します。文書の業務境界との対応も明示し、コンテキストをプロセスやサービスへ一対一に割り当てません。
- テーマ別設計で必要に応じてエンティティ、値オブジェクト、集約、ドメインサービス、リポジトリ、ドメインイベントを選びます。全パターンを必須にせず、モデルの責務・振る舞い・採用理由を示します。アプリケーションの調整処理や技術的な処理と業務ルールを区別します。
- 集約は不変条件と整合性を守る更新単位から検討し、集約ルート・所有・参照・更新境界を必要な範囲で明示します。クラスやDBテーブルとの機械的な一対一対応を避け、ドメインモデルと永続化モデルの対応・変換を示します。
- 共通モデルの一元化は同一コンテキスト内を基本とします。コンテキストをまたぐ同名概念は別の意味を許容し、必要な変換・連携契約を設計します。共有モデルを採用する場合は根拠・責務・変更影響を明示します。
- 論理的連携を入力に必要なAPI・イベントの技術契約を設計し、要件上の期待結果と失敗時の振る舞いを維持します。業務イベントをすべて外部配信する必要はありません。
- 用語の意味の変更は要求担当へ、業務ルール・論理的境界の変更は要件担当へ返し、必要な調整と上流反映まで確定しません。既存の全体設計・テーマ別設計・データ構造・テスト方針の枠に記録し、DDD専用の並行したDES台帳は作りません。
- 完了確認とテスト方針に用語・モデル・技術契約の対応、不変条件と集約の整合性、必要なコンテキスト間変換の確認を含めます。具体的なテスト計画・コード・実行は従来どおり別担当へ引き継ぎます。

## DDDの確認シナリオ

以下は指示・文書のレビュー観点です。実際のエージェント実行・受入試験を実施した結果とは区別します。

| 入力・状況 | 期待する対応 |
| --- | --- |
| 単一コンテキスト | 必要なモデルだけを選び、サービス分割や全戦術パターンを強制しない |
| 同名異義の用語 | コンテキストごとの意味を維持し、必要な変換・技術契約を設計する |
| 未合意の論理的境界 | 要件担当へ確認を返し、独立した設計だけ進める |
| 設計中の業務ルール変更 | 無断で確定せず、要件担当へ根拠・影響とともに返す |
| イベント配信が不要 | 業務上の出来事を理由にメッセージ基盤やイベントソーシングを採用しない |
| 集約・永続化設計 | 不変条件と更新単位を根拠とし、集約・クラス・テーブルを機械的に一致させない |
| DDD資料が未作成 | 既存REQの合意を取り消さず、判明範囲を提案として整理し必要な意味の判断を返す |
| 設計中に用語の意味を変更 | 要求担当へ案・根拠・関連REQ/DESを返す。業務ルール・境界にも影響する場合は要件担当との調整を依頼し、反映結果を確認して設計を更新する |
